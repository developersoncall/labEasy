Medis Database Guide

Everything you need to provision the shared Supabase project that powers both the Medis patient website (this repository) and the Medis Diagnostics admin panel (labadmin-b1090.web.app) — schema, security policies, storage, auth and realistic seed data, in one idempotent SQL script.

01Overview & Architecture#

One Supabase project backs two separate frontends. They talk to the same tables but with very different privileges:

🩺 Patient Website (this repo)

Vite + React 18 SPA. Connects with the anon key as anon / authenticated roles.

Every query passes through Row Level Security: catalog tables are world-readable, personal tables are visible only to their owner (auth.uid() = user_id).

Reads: doctors, specialties, tests, packages, blogs, FAQs, testimonials. Writes: appointments, lab bookings, reviews, favorites, profiles, notifications, contact messages.

This database is required — the site has no offline or demo fallback and shows a setup screen until Supabase credentials are configured.

🧑‍💼 Admin Panel (labadmin-b1090.web.app)

“Medis Diagnostics” back office. Connects with the service-role key, which bypasses RLS entirely — it must never ship in browser-exposed code without a trusted backend.

Modules mapped to tables: Dashboard KPIs & Bookings → booked_tests; Home Collections / Lab Visits → booked_tests.collection_type; Reports → medical_reports; Doctors → doctors; Users → user_profiles; Payments & Billing → payments; Categories → test_categories; Support Tickets → contact_messages; Banners/CMS & Settings → settings.

🔑
Key design decision: the admin workflow states live in shared enums and lookup tables — booking_status_enum (pending → confirmed → sample_collected → processing → report_ready → completed / cancelled), report_status_enum (pending → processing → verified → signed) and the appointment_status lookup table. The patient site renders these states read-only (via StatusBadge); the admin panel advances them with the service-role key.

02Step-by-Step Setup#

From zero to a fully-seeded database in about five minutes.

1

Create a Supabase project

Go to supabase.com/dashboard → New project. Pick your organization, name it (e.g. medis), set a strong database password and choose the region closest to your users (e.g. ap-south-1 Mumbai for India). Wait ~2 minutes for provisioning.

📷 Screenshot cue
The dashboard shows a green “Project Status: Active” badge in the top bar once provisioning finishes. Until then, the SQL Editor is unavailable.
2

Open the SQL Editor

In the left sidebar choose SQL Editor → New query. You get a blank editor with a Run button (or press Cmd/Ctrl + Enter).

📷 Screenshot cue
Sidebar order in the dashboard: Table Editor · SQL Editor · Database · Auth · Storage · Edge Functions. You want the second item, the terminal-style icon.
3

Paste the complete script and Run

Click Copy on the Complete SQL Script below, paste it into the editor and hit Run. It executes top-to-bottom in one pass — extensions → enums → tables → triggers → RLS → storage → seeds. Expect a “Success. No rows returned” style message after a few seconds.

✅
The script is idempotent — running it a second time is harmless. Tables use IF NOT EXISTS, functions use OR REPLACE, and every seed insert ends in ON CONFLICT DO NOTHING.
4

Grab your Project URL and anon key

Go to Project Settings → API. Copy two values: Project URL (looks like https://YOUR-PROJECT-REF.supabase.co) and the anon public API key (a long JWT starting with eyJ…).

📷 Screenshot cue
The API page shows three keys: anon public (safe for the browser — this is the one you want), service_role (server/admin only — used by the admin panel, never by this website) and the JWT secret.
⛔
Never put the service_role key in this repo or any browser bundle. It bypasses every RLS policy. Only the admin panel’s trusted environment should hold it.
5

Configure .env and restart

In the project root, copy .env.example to .env and fill in the two values, then restart the dev server:

.env
VITE_SUPABASE_URL=https://YOUR-PROJECT-REF.supabase.co
VITE_SUPABASE_ANON_KEY=eyJhbGciOiJIUzI1NiIsInR5cCI6...

The client in src/supabase/supabase.js detects real credentials automatically. Until they are set the site shows a setup screen rather than any data — Supabase is required and there is no offline or demo fallback.

6

Enable auth & verify

Follow the Auth Setup section (email provider + redirect URLs), then run the verification queries to confirm the seed row counts.

-- 4.1 updated_at maintenance — one function, applied to every table above
create or replace function public.set_updated_at()
returns trigger
language plpgsql
as $$
begin
  new.updated_at = now();
  return new;
end;
$$;

do $$
declare t text;
begin
  foreach t in array array[
    'user_profiles','specialties','doctors','doctor_specialties','appointments',
    'test_categories','diagnostic_tests','health_packages','booked_tests',
    'medical_reports','prescriptions','reviews','favorites','notifications',
    'blogs','faqs','testimonials','contact_messages','payments','settings'
  ] loop
    execute format('drop trigger if exists set_updated_at on public.%I', t);
    execute format(
      'create trigger set_updated_at before update on public.%I
         for each row execute function public.set_updated_at()', t);
  end loop;
end $$;

-- 4.2 Auto-create a user_profiles row whenever someone signs up.
--     SECURITY DEFINER so it can insert regardless of the calling RLS context.
--     Copies full_name / phone from the signup metadata sent by the website.
create or replace function public.handle_new_user()
returns trigger
language plpgsql
security definer
set search_path = public
as $$
begin
  insert into public.user_profiles (user_id, full_name, phone)
  values (
    new.id,
    coalesce(new.raw_user_meta_data->>'full_name', ''),
    coalesce(new.raw_user_meta_data->>'phone', '')
  )
  on conflict (user_id) do nothing;
  return new;
end;
$$;

drop trigger if exists on_auth_user_created on auth.users;
create trigger on_auth_user_created
  after insert on auth.users

-- 4.3 Keep doctors.rating / review_count in sync with approved reviews.
--     SECURITY DEFINER because patients (who insert reviews) have no UPDATE
--     policy on doctors — the trigger does the update on their behalf.
--     NOTE: the seeded review_count values are display placeholders; the first
--     real review recalculates both columns from actual approved reviews.
create or replace function public.refresh_doctor_rating()
returns trigger
language plpgsql
security definer
set search_path = public
as $$
declare
  d uuid;
begin
  d := coalesce(new.doctor_id, old.doctor_id);
  update public.doctors set
    rating = coalesce(
      (select round(avg(rating)::numeric, 1) from public.reviews
        where doctor_id = d and is_approved),
      rating),
    review_count = (select count(*)::int from public.reviews
                     where doctor_id = d and is_approved)
  where id = d;
  return coalesce(new, old);
end;
$$;

drop trigger if exists refresh_doctor_rating on public.reviews;
create trigger refresh_doctor_rating
  after insert or update or delete on public.reviews
  for each row execute function public.refresh_doctor_rating();

declare
  cfg record;
  r   record;
begin
  for cfg in
    select * from (values
      ('booked_tests',    'booking_ref',     'BK', 'ref_seq_booked_tests'),
      ('appointments',    'appointment_ref', 'AP', 'ref_seq_appointments'),
      ('medical_reports', 'report_ref',      'RP', 'ref_seq_medical_reports'),
      ('payments',        'payment_ref',     'PY', 'ref_seq_payments'),
      ('user_profiles',   'user_ref',        'US', 'ref_seq_user_profiles'),
      ('staff',           'staff_ref',       'ST', 'ref_seq_staff'),
      ('contact_messages','ticket_ref',      'TK', 'ref_seq_contact_messages')
    ) as t(tbl, col, prefix, seq)
  loop
    execute format('alter table public.%I add column if not exists %I text', cfg.tbl, cfg.col);
    execute format('drop index if exists public.%I', cfg.tbl || '_' || cfg.col || '_idx');
    execute format('create sequence if not exists public.%I', cfg.seq);
    execute format('alter sequence public.%I restart with 1', cfg.seq);
    execute format('update public.%I set %I = null', cfg.tbl, cfg.col);
    for r in execute format('select id from public.%I order by created_at, id', cfg.tbl)
    loop
      execute format(
        'update public.%I set %I = %L where id = %L',
        cfg.tbl, cfg.col,
        cfg.prefix || lpad(nextval('public.' || cfg.seq)::text, 2, '0'),
        r.id
      );
    end loop;
    execute format(
      'alter table public.%I alter column %I set default %L || lpad(nextval(%L)::text, 2, %L)',
      cfg.tbl, cfg.col, cfg.prefix, 'public.' || cfg.seq, '0'
    );
    execute format('create unique index if not exists %I on public.%I(%I)',
                   cfg.tbl || '_' || cfg.col || '_idx', cfg.tbl, cfg.col);
  end loop;
end $$;

05Row Level Security#

RLS is enabled on every table. The patient site connects with the anon key, so these policies are the entire security boundary between users. The admin panel connects with the service-role key, which bypasses RLS completely — that is by design, and it is why that key must never reach a browser.

🛡️
Why UPDATE but no DELETE on user data? Patients cancel bookings by flipping status to cancelled (exactly what appointmentService.cancel() and diagnosticService.cancelBooking() do) — the row is preserved for the admin panel’s KPIs, payments trail and audit history. Only favorites genuinely deletes rows.
⚠️
Two write paths worth knowing: ① the signup profile row is inserted by the handle_new_user trigger (SECURITY DEFINER), not by the client; ② review inserts update doctors.rating via the refresh_doctor_rating trigger (SECURITY DEFINER) because patients have no UPDATE policy on doctors.

The policy DDL (already part of the complete script):

rls_policies.sql
-- Catalog tables: world-readable
do $$
declare t text;
begin
  foreach t in array array[
    'specialties','doctors','doctor_specialties','diagnostic_tests',
    'test_categories','health_packages','blogs','faqs','appointment_status','settings'
  ] loop
    execute format('alter table public.%I enable row level security', t);
    execute format('drop policy if exists "Public read" on public.%I', t);
    execute format(
      'create policy "Public read" on public.%I
         for select to anon, authenticated using (true)', t);
  end loop;
end $$;

-- testimonials: public read of active rows only
alter table public.testimonials enable row level security;
drop policy if exists "testimonials are public" on public.testimonials;
create policy "testimonials are public"
  on public.testimonials for select
  to anon, authenticated
  using (is_active = true);

-- User-owned tables: owner-scoped SELECT / INSERT / UPDATE
do $$
declare t text;
begin
  foreach t in array array[
    'user_profiles','appointments','booked_tests','medical_reports',
    'prescriptions','notifications','favorites','payments'
  ] loop
    execute format('alter table public.%I enable row level security', t);
    execute format('drop policy if exists "Owner select" on public.%I', t);
    execute format(
      'create policy "Owner select" on public.%I
         for select to authenticated using (auth.uid() = user_id)', t);
    execute format('drop policy if exists "Owner insert" on public.%I', t);
    execute format(
      'create policy "Owner insert" on public.%I
         for insert to authenticated with check (auth.uid() = user_id)', t);
    execute format('drop policy if exists "Owner update" on public.%I', t);
    execute format(
      'create policy "Owner update" on public.%I
         for update to authenticated
         using (auth.uid() = user_id) with check (auth.uid() = user_id)', t);
  end loop;
end $$;

-- favorites: users may also un-favorite
drop policy if exists "Owner delete" on public.favorites;
create policy "Owner delete" on public.favorites
  for delete to authenticated using (auth.uid() = user_id);

-- reviews: public read of approved reviews, owner-scoped insert
alter table public.reviews enable row level security;

create policy "Public read approved" on public.reviews

06Storage Buckets#

Two buckets, two very different trust models. Files are namespaced by folder: the first path segment is always the owner’s user_id, which is what the policies check via storage.foldername(name)[1].

🖼️ avatars — public

Profile photos uploaded by profileService.uploadAvatar() to {user_id}/{timestamp}_{filename}.

Read: everyone (the site renders avatars via getPublicUrl).
Write/Update/Delete: only into your own {user_id}/ folder.

📄 reports — private

Lab report PDFs uploaded by the admin panel to {user_id}/{report}.pdf; medical_reports.report_url references them.

Read: owner only (path must start with their user_id).
Write: service role only — there is deliberately no insert policy, so anon/authenticated writes are denied.

values ('avatars', 'avatars', true)
on conflict (id) do nothing;

values ('reports', 'reports', false)
on conflict (id) do nothing;

Troubleshooting

SymptomCause & fix
Ran the script twice and it errored on a seedIt should not — all seeds use ON CONFLICT DO NOTHING. If you edited a seed and removed its conflict clause, restore it, or delete the duplicate rows and re-run.
relation "…" already existsYou are running an older draft without if not exists. Use the script from this page verbatim — every create table/create index carries if not exists.
type "…_enum" already existsHarmless if using this script (enums are wrapped in do $$ … exception when duplicate_object). Otherwise wrap your create type the same way.
Website shows doctors/tests in demo mode but the database is empty-lookingThe .env values are missing or wrong, so isSupabaseConfigured is false and the app silently uses local constants. Check VITE_SUPABASE_URL starts with https:// and restart npm run dev — Vite only reads .env at startup.
Catalog loads but “My Appointments/Bookings/Reports” are always emptyThat is RLS working: you are reading rows whose user_id is not yours (or you inserted sample rows with the wrong UUID). Verify the UUID in the optional seed block matches Authentication → Users.
All reads fail with permission denied / empty arrays even for doctorsRLS got enabled without the read policies (or policies were dropped). Re-run section 5 of the script — the policy blocks are idempotent.
new row violates row-level security policy on bookingThe insert’s user_id does not equal auth.uid(). Make sure the user is logged in (not demo mode) and the session token has not expired.
